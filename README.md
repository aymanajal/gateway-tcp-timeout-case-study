# 一次间歇性连接超时排查 从发票报错到TCP旧连接残留

最开始，前台只有一句报错：**第三方厂商异常**。

用户上传发票，或者开票后发送到税务平台，偶尔就会遇到这个提示。有时重试成功，有时还要再等一会儿。单看页面，很容易把它理解成第三方接口不稳定。

但沿着调用链查下去，我们发现，有些失败请求在网关应用日志里根本找不到。后来通过循环测试、双端抓包、连接状态对照和固定源端口复现，问题逐渐收窄到一类具体异常：**客户端已经没有的TCP连接，网关服务器仍然保留着。当相同四元组再次用于建连时，服务端按旧连接状态回应，新连接无法完成握手。**

厂商随后提供了补丁，在网关入站监听上增加120秒空闲超时。补丁后的测试有了变化，但仍留下一个需要继续追踪的超时样本。

这篇文章把发现、取证、走过的弯路、补丁修改和验证过程放在一起。写到这里，问题还没有全部关闭。我更希望保留每一步判断的依据，而不是把尚未完成的排查写成一个已经解决的故事。

> 企业、厂商、部署路径、地址、端口及请求标识均已匿名化。文中的地址使用文档示例地址，端口和TCP序列号也经过替换；示例命令需要改成自己的测试环境。测试次数及成功失败数量保留实际统计。以下报文是依据真实记录整理的脱敏示意，不是原始生产日志。

## 1 先把报错放回调用链

当时的业务链路是：

```text
ERP应用服务器 → 内网网关 → 第三方税务平台
```

前台的“第三方厂商异常”是应用在调用超时后转换出来的提示。它告诉我们调用失败了，但并不能直接指出是第三方业务报错、网关转发失败，还是应用到网关之间连TCP都没建立起来。

第一条有价值的线索是：应用侧出现超时的时间附近，网关业务日志没有对应记录。

这还不能直接证明请求没有到达服务器。可能是日志没有覆盖入口，也可能是查错了文件、实例或时间段。于是我们先把问题简化：暂时不通过发票上传制造故障，而是在应用服务器上直接访问网关的一个无业务测试接口。

这个接口只返回固定的HTTP 200和一段成功文本，不再转发下游。后面通过包内代码也核对了这一点。不过，它仍然经过共享路由和中间件，不能把它说成与网关其他资源完全隔离。

这次简化很有用。它让我们可以持续观察“应用服务器到网关入口”这一段，不需要每次准备一张发票，也不会因为税务平台返回了什么，把最前面的连接问题掩盖掉。

## 2 循环调用后 发现失败发生在建连阶段

最初是手动执行curl。一次成功，一次超时，偶发问题很难靠几次手工操作判断，于是改成循环调用，并记录每次的时间、连接耗时、首字节耗时、总耗时和退出码。

下面是一份适合测试环境的简化版。在一台应用服务器上运行，按Ctrl+C停止：

```bash
TARGET_URL='http://203.0.113.20:18080/openapi/test'
PROBE_HOST=$(hostname | tr -cd 'A-Za-z0-9_.-')

while true; do
  PROBE_ID="${PROBE_HOST}-$(date +%s%N)"
  echo
  echo "[$(date '+%F %T.%N %z')] probe_id=${PROBE_ID}"

  curl --noproxy '*' -sS --connect-timeout 5 --max-time 10 \
    -w '\nlocal=%{local_ip}:%{local_port} remote=%{remote_ip} HTTP=%{http_code} connect=%{time_connect}s TTFB=%{time_starttransfer}s total=%{time_total}s\n' \
    "${TARGET_URL}?probe_id=${PROBE_ID}"

  CURL_CODE=$?
  echo "curl退出码=${CURL_CODE} probe_id=${PROBE_ID}"
  sleep 5
done 2>&1 | tee "curl-probe-$(date +%Y%m%d-%H%M%S).log"
```

这份简化版是每次请求结束后等待5秒，不是严格每5秒开始一次。现场后续的脚本做了开始时间调度，请求慢时仍然不并发。两种方式都能取证，但统计请求间隔时要分清楚。

测试中反复出现这样的失败组合：

```text
Connection timed out after 5001 milliseconds
HTTP=000
connect=0.000000s
TTFB=0.000000s
total=5.001xxx s
curl退出码=28
```

这里要结合错误文本和计时一起看。curl退出码28也可能用于其他超时；这批样本明确提示连接超时，且耗时落在设置的5秒连接时限附近。

**这些请求没有建立起可用的TCP连接，还没走到HTTP接口处理阶段。**`HTTP=000`是curl没有取得HTTP状态码的表现，不是服务端返回了一个名为000的状态。

这也解释了为什么网关业务日志里可能没有记录：HTTP请求尚未发进去，业务处理器自然无从记录这次调用。

## 3 Ping很稳定 为什么curl还会失败

排查期间，我们也做了持续ping。大部分延迟很低，整体看起来很稳定。

这个结果有意义：至少在这些采样时刻，ICMP往返是正常的。但它不能替代TCP建连测试。

Ping不访问网关业务端口，不执行TCP三次握手，也不核对服务器是否保留着某条旧TCP连接。因此，ping稳定和某些TCP连接失败可以同时存在。

网关本机调用自己也曾得到一段全部成功的测试结果。但是，自调用的路径和远端应用服务器不同，测试时间段也不完全相同。它能提供对照，不能据此把远端的间歇性失败排除掉。

到了这里，继续争论“网络是不是通的”已经不够具体。我们需要看同一次失败中，双方到底发了什么、收到了什么。

## 4 双端抓包后 看到了不符合新握手的ACK

我们开始在客户端和网关服务器两端同时抓包。

现场最初还遇到工具不齐、抓包目录权限等问题。服务端早期没有tcpdump时，使用过Python标准库的AF_PACKET采集报文；后续具备tcpdump后，再用双端pcap对照。采集工具可以变化，但四元组、方向、时间和TCP序列号必须保留下来。

下面是双端抓包的基本形式。先启动两端抓包，再启动循环调用：

```bash
# 客户端 示例地址需替换
sudo tcpdump -nn -i any -s 128 -B 4096 -U \
  -w client.pcap \
  'tcp and host 203.0.113.20 and port 18080'

# 网关服务器 限定同一客户端的双向流量
sudo tcpdump -nn -i any -s 128 -B 4096 -U \
  -w server.pcap \
  'tcp and host 198.51.100.10 and port 18080'
```

在有权限访问的测试环境使用，先确认目录可写。128字节截断长度主要用于保留TCP头，不保证保存完整HTTP路径或正文；如果需要业务层关联，应另行设计采集范围。

正常建连应该是：

```text
客户端                    服务端
  | -------- SYN ---------> |
  | <----- SYN,ACK --------- |
  | -------- ACK ---------> |
  | ------ HTTP请求 ------> |
```

但失败样本里出现了另一种过程：

```text
客户端                    服务端
  | -------- SYN ---------> |
  | <----- 普通ACK -------- |
  | -------- RST ---------> |  客户端抓包可见 服务端抓包未见
  | ------ 重传SYN -------> |
  |         ……             |
  |     约5秒后建连超时     |
```

举一个替换过序号的示意：新SYN的序列号是1000，正常SYN、ACK应确认1001。实际返回的却是一个没有SYN标志的普通ACK，确认号属于另一组序列空间，比如9000。

这个回应明显不属于本次正常的新握手。结合后面的连接状态，它符合服务端仍按旧连接状态处理新SYN的表现。RFC 5961第4.2节也描述了同步状态连接收到SYN时发送challenge ACK的处理；它可以帮助理解这种现象，但仅凭一条普通ACK，不能认定所有环境都是同一种原因。[RFC 5961](https://www.rfc-editor.org/rfc/rfc5961.html#section-4.2)

双端抓包还有一个关键差异。更新前的一轮抓包，客户端看到了61条发出的RST，服务端没有看到RST；更早的一轮也有22条对0条的情况。

这说明RST在两个采集点之间的可见性不同。**它还不能直接指出丢弃发生在哪一台设备。**客户端本机抓到了出站报文，也不等于报文已经实际离开物理网卡。两端还要核对共同采集窗口和抓包丢包统计，不能只比较总数。

## 5 服务端ESTAB 客户端却没有对应连接

抓包让我们开始怀疑旧连接状态，于是用ss核对双方的连接表。

判断对象是一条具体的TCP四元组：

```text
客户端IP  客户端源端口  服务端IP  服务端端口
```

例如，下面这组示例地址和端口：

```text
198.51.100.10:45000 → 203.0.113.20:18080
```

在网关服务器上查：

```bash
ss -ntopi \
  'sport = :18080 and dst 198.51.100.10 and dport = :45000'
```

在客户端查：

```bash
ss -ntopi \
  'dst 203.0.113.20 and dport = :18080 and sport = :45000'
```

两边查询应尽量同时执行，并确认检查的是同一客户端、同一网络命名空间。实际样本中，网关一侧仍有ESTAB连接，归属于网关Java进程；客户端一侧已经没有对应socket。多组连接都出现过这种状态差异。

部分样本的`lastsnd`、`lastrcv`已经达到十几个小时。后来有一条与失败抓包直接对应的连接，距数据活动约五个多小时，仍然保留在服务端。

这里也纠正了一个容易混淆的地方：`lastsnd`、`lastrcv`表示距最近数据活动的时间，单位是毫秒，**不是连接建立至今的年龄**。单纯空闲很久也不等于异常。更有力的证据是：同一四元组，服务端仍为ESTAB，客户端已经不存在。

对于这条样本，我们已经不只是在看“连接数很多”，而是找到了两端状态不一致的具体连接。

## 6 固定源端口 把偶发变成可重复验证

前面的循环测试还需要等待偶发超时。找到残留连接对应的客户端源端口后，我们做了一个更直接的对照。

先确认客户端没有占用这个源端口，再在单次诊断中固定使用它：

```bash
curl --noproxy '*' --local-port 45000 -v \
  --connect-timeout 5 --max-time 10 \
  http://203.0.113.20:18080/openapi/test
```

然后让curl自动分配源端口：

```bash
curl --noproxy '*' -v \
  --connect-timeout 5 --max-time 10 \
  http://203.0.113.20:18080/openapi/test
```

现场结果是：

| 调用方式 | 结果 |
|---|---|
| 固定使用服务端仍保留旧连接的源端口 | 约5秒后连接超时 |
| 自动分配源端口 | 立即建连成功，HTTP 200 |

如果固定端口时提示绑定失败，这次测试就无效，不能算成我们要复现的故障。固定端口也只用于定点诊断，不应当直接拿去替换正常业务客户端配置。

这个对照把问题收窄了：服务端并非整体无法服务；失败与特定四元组的旧连接状态直接相关。

它还没有证明RST具体丢在哪里，也没有把每一笔发票超时都逐笔关联上。但对于这类入口建连失败，我们已经有了具体连接、报文和可重复的测试条件。

## 7 排查过程中 几个看似相关但不能直接定因的指标

### FD上限很高 不等于连接清理正常

我们曾怀疑网关是不是连接池满了，也查过Java进程的文件描述符：

```bash
# 将PID替换为实际监听进程
ls /proc/PID/fd | wc -l
grep 'open files' /proc/PID/limits
```

当时允许打开的FD约55万，实际使用不到1万。这不支持“采样时FD已经耗尽”的判断。

但是FD包括socket和文件等资源，不是精确的TCP连接数，也不是某个HTTP连接池的容量。FD余量充足，同样可以存在失去对端的旧socket。反过来，某个连接池排队也不一定会把整个进程的FD用尽。

### 累计监听丢弃数 不能直接解释这次失败

系统的`ListenOverflows`、`ListenDrops`曾有较高的历史累计值，但某段观察期没有增长。

这类计数需要看失败窗口内的增量，还要注意它们不是天然按某一个业务端口统计。历史累计值大，不能直接证明当前端口正在因队列满而丢弃连接；一个非故障窗口没有增长，也不能替代每次失败时的核对。

### 其他服务的超时 不能直接套到发票链路

网关日志里还发现过另一项本机服务的连接获取超时。查进程、目录和日志后，发现它属于协同服务。

它同样值得处理，但没有证据把它与这次发票失败关联起来。我们一度在这条支线上花了时间，后来又把排查拉回“应用到网关入口的TCP建连”。

同一台服务器上有多个异常，不等于它们就是同一个故障。

### 本机规则没有命中 不等于所有过滤位置都排除了

后来检查了两端iptables、nftables、网卡和TC信息，没有发现能够解释这批RST差异的过滤规则。客户端的BPF网络挂载列表为空；服务端查询工具版本受限，不能把所有BPF相关位置都宣布排除。

网卡的历史丢弃计数也只能作线索，不能直接对应某一条RST。我们没有据此给某个设备或团队下结论。

## 8 旧连接为什么能保留这么久

TCP可以有正常的长期空闲连接。服务端如果没有收到有效的关闭或重置信息，也没有主动发送数据，并不一定会很快发现对端已经不存在。

所以我们接着检查：网关有没有主动回收空闲连接，或者启用TCP keepalive。

在这条旧连接的ss输出里，没有看到keepalive定时器。系统参数倒是有：空闲7200秒开始探测，间隔75秒，允许9次探测失败。

但这些系统参数只对启用了TCP keepalive的socket生效。系统设置了时间，不代表每条连接都会自动获得保活机制。ss快照里没显示定时器只是一条线索，还需要结合程序创建socket时的配置判断。

为此，我们离线检查了厂商安装包和适配器。找到实际提供测试接口的入站服务后，旧版创建监听的关键逻辑等价于：

```java
HttpServerOptions options = new HttpServerOptions()
    .setPort(port);
```

这里没有显式设置空闲超时，也没有启用TCP keepalive。提供的Vert.x 3.9.10核心库默认值是：

```text
idleTimeout = 0
idleTimeoutUnit = SECONDS
tcpKeepAlive = false
```

其中0表示不启用该空闲超时。我们既核对了实际库的默认值，也参考了相同版本的公开源码。[Vert.x 3.9.10 TCPSSLOptions](https://github.com/eclipse-vertx/vert.x/blob/3.9.10/src/main/java/io/vertx/core/net/TCPSSLOptions.java)

现场旧适配器和核心库的SHA256也与本地分析文件一致。哈希确认了磁盘文件身份；运行中是否加载了同一份文件，还要结合进程启动时间和适配器加载路径。

由此能够补上一段解释：**关闭信息未被正常处理时，这个入站服务缺少通过上述配置主动回收空闲连接的兜底机制。**

它解释了旧状态为什么可能长期保留，仍然没有解释RST为什么没有出现在服务端抓包里。传输问题和清理机制不足可以同时存在。

还有一个细节：当时尝试过用`ss -K`只关闭这条已经失去客户端的旧连接，但执行后它依旧存在。最后检查内核配置，发现：

```text
CONFIG_INET_DIAG=m
CONFIG_INET_TCP_DIAG=m
# CONFIG_INET_DIAG_DESTROY is not set
```

内核没有启用相应的socket销毁能力。对应版本的ss对部分“不支持”等返回可能不显示明显错误，所以只打印表头不能作为清理成功的依据，必须再查询连接表。[iproute2 ss源码](https://github.com/iproute2/iproute2/blob/v5.4.0/misc/ss.c)

因此，“清掉旧连接再用同一端口测试”这一步没有完成，不能把它写成成功的修复实验。缺少这个内核选项也只是清理工具失效的原因，不是正常TCP连接为什么残留的原因。

## 9 厂商补丁具体改了什么

厂商后来提供了两个新JAR。我们没有只看文件名，而是比较新旧包里的class，再对变化的类反编译，并用字节码复核关键修改。

与这次问题最直接相关的一处变化，是入站HTTP服务增加了空闲超时：

```java
HttpServerOptions options = new HttpServerOptions()
    .setPort(port)
    .setIdleTimeout(120);
```

120直接写在代码里，单位为秒，不是通过给旧配置文件随手增加一个同名字段实现的。新版这里仍然没有新增`setTcpKeepAlive(true)`。

本地核对HTTP/1的底层初始化代码，空闲处理器使用的是整体读写空闲检测。用直白的话说：**连续约两分钟没有应用数据读写，就主动关闭这条连接。**

这不等于每个请求都只能执行120秒。持续有数据传输的连接可以存在更久；但如果请求已提交、下游长时间处理，双方连续120秒没有数据，这个改动也可能影响它，因此必须验证业务兼容性。

它针对的是旧连接积累：即使关闭或重置没有正常完成，也不再允许没有数据活动的ESTAB无限期保留。它缩短了旧状态占用四元组的时间，但并不保证两分钟以内绝不发生冲突，更不会自动修复某个采集点之间的RST差异。

另外还发现了几处修改：

| 修改 | 可以确认的作用 |
|---|---|
| 启动准备阶段不再调用清空适配器缓存的方法 | 启动时不再主动删除该目录里的适配器文件 |
| 云端WebSocket默认单帧上限从10 MiB改为50 MiB | 扩大默认单帧接收上限，不等于发票附件上限直接变为50 MB |
| 部分文件配置接口日志增加traceId | 更方便关联该路径的请求、返回参数和错误 |

这些改动不能都归到“旧连接问题已修复”下面。主客户端POM和清单还有依赖声明变化，但只拿到两个业务JAR，也不能证明部署目录中的所有依赖都已经同步更新。

我们还需要核对现场新包的哈希和实际加载路径。下面的复测结果发生在现场更新之后；是否与后来交给我们分析的两个文件完全一致，需要这一步版本确认。

## 10 更新后跑了半小时 359次成功 1次仍然超时

现场更新之后，应用服务器继续每5秒发起一次测试，持续约半小时，同时保留两端抓包。

| 项目 | 结果 |
|---|---|
| 请求次数 | 360次 |
| 成功 | 359次，HTTP 200 |
| 失败 | 1次，约5秒连接超时 |
| 成功请求总耗时中位数 | 约2.9毫秒 |
| 成功请求最长耗时 | 约1.10秒 |

这轮有两个值得分开看的变化。

第一，**没有再发现此前那种“新SYN收到旧连接普通ACK”的模式**。客户端抓到的389条RST，都能在服务端抓包中找到对应报文。两轮测试的时段、负载和运行状态不同，不能把RST重新可见全部归功于新JAR，也不能直接拿两轮失败比例计算补丁修复率。

第二，那一次测试失败的报文表现变了：客户端发出了初始SYN，并在约1秒、3秒后重传，服务端抓包没有看到这三条SYN，客户端最终在约5秒后超时。

它不再是之前那条旧连接冲突的报文链。因为当时没有保留两端tcpdump结束时的内核丢包统计，还不能直接区分链路未送达和抓包自身漏采。

同一批抓包里还存在其他业务请求，不能把整个pcap中的HTTP 500数量直接当成这360次测试的失败数。统计必须按测试标识、四元组和时间窗口对应。

更新后还有一次连接快照：870条ESTAB，没有超过1小时未收发数据的连接。这比之前十几个小时的空闲残留更好，但仍不足以证明120秒清理已生效：如果更新时重启了网关，重启本身也会清掉旧连接。况且“没有超过1小时”远比我们真正要验证的“两分钟”宽松。

所以这次处理后的状态应该写成：**已增加针对长期空闲连接的回收机制；更新后的短时测试没有复现旧模式，但仍存在另一类待定位的建连异常。**

没有理由在这里写“所有问题彻底解决”。

## 11 接下来怎样把验证做完整

后续验证需要同时覆盖补丁本身、连接长期运行和真实业务。

先确认实际运行版本。记录监听进程、启动时间、JAR哈希及适配器加载路径。如果同名或不同版本适配器同时存在，不能因为目录里多了一个新文件，就认定它已经生效。

接着只建立一条TCP连接，不发送业务数据，观察它是否在约120秒后被服务端关闭。重复几次，同时在网关查询同一四元组，必要时用短时抓包确认关闭方向。客户端收到EOF或RST的时间，只代表客户端的观察，仍要排除其他设备主动关闭的可能。

然后继续跑测试接口，覆盖至少6至8小时和一个正常业务高峰，再做跨夜观察。每隔几分钟记录连接总数、状态和空闲分组。既然补丁是120秒，统计就应该增加“超过3分钟”和“超过10分钟”，而不是只统计超过一小时。

这里仍需区分：数据空闲多久、连接建立多久、连接是否真的失去对端，是三个不同问题。发现长时间ESTAB后，再到客户端核对同一四元组。

最后回到最初的发票业务。上传和开票自然发生时，保留准确时间、单据标识、请求标识和结果。如果再失败，先区分TCP有没有建立、HTTP有没有到网关、网关有没有转发，以及下游如何返回。测试接口成功，不能替代发票上传和开票成功。

长时间抓包也要控制采集量。这次半小时双端pcap已经接近500 MB，直接延长到全天会增加存储和分析负担。后续应按时间或大小轮转，保留每段的采集统计；定点复现可以限定源端口。只抓TCP控制报文会减小体积，也会失去部分HTTP关联信息，取舍需要提前写清。

## 12 这次排查中 我们真正改变了哪些判断

最开始，看到前台“第三方异常”，我们自然会去找第三方调用错误。后来发现请求可能连网关应用都没进入，排查才转到入口TCP。

看到ping稳定时，容易觉得网络没有问题；看到ESTAB很多时，又容易怀疑连接池满。把判断落到同一条连接的报文和两端状态后，才发现它们都不是足够准确的解释。

固定源端口的对照，是这次最有帮助的一步。它把“偶尔不通”变成一个具体条件：同一个旧四元组失败，换一个源端口成功。随后对程序的检查，又补上了为什么这种状态能长期保留的机制线索。

处理上，我们拿到了增加120秒空闲超时的补丁。对于RST曾经为什么没有出现在服务端、更新后那条SYN未见的连接又卡在哪里，仍需要继续取证。

写下这些，是因为生产排障很少会在一张图、一条命令之后结束。能确认的处理效果要验证，尚未定位的位置要留着。只有把这两部分分清，后面的同事才知道该从哪里继续，而不是从头再猜一次。
